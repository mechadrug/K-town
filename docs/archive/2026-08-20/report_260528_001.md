# K-town 多 Agent 模拟小镇项目初步分析报告

Date: 2026-05-28

## 1. 项目命题

K-town 可以先定义为：

> 一个多智能体小镇模拟游戏。开发者只设定世界规则、资源、初始人物和事件种子；小镇居民通过感知、记忆、交互、学习、传播知识和创造物品，逐渐形成自己的社会结构。玩家既可以旁观，也可以作为真人居民进入其中，和 agent 共同改变世界。

核心不是“1000 个 LLM NPC 同屏聊天”，而是“一个会积累知识、关系和历史的小镇系统”。

README 中已经提出了关键方向：镇子上的人不应只是玩家视角里的 NPC，而应该遵循小镇规则、基于自己的想法做决策和行动。后续设计需要围绕这个目标收敛：让小镇居民具备持续状态、记忆、知识、目标和社会关系，而不是只做单次对话。

## 2. 当前想法的可落地拆分

建议把当前想法拆成五个可实现系统。

### 2.1 环境系统

小镇由地点、资源、规则和事件组成。

第一版可以只包含少量地点：

- 广场：公共信息、集会、公告。
- 学校或档案馆：知识记录、学习、历史查询。
- 工坊：制作物品、工具改良。
- 商店：资源交换、价格变化。
- 森林或矿洞：探索、危险、未知知识来源。

每个地点都应有：

- 可观察信息。
- 可执行动作。
- 可产生事件。
- 可影响 agent 状态的规则。

### 2.2 Agent 系统

每个 agent 至少应有以下结构：

- 身份：姓名、职业、性格、目标、禁忌。
- 状态：体力、情绪、金钱、关系、当前任务。
- 记忆：短期记忆、长期记忆、事件摘要。
- 知识：个人知道什么、相信什么、会什么。
- 行为策略：日程、目标选择、社交倾向、风险偏好。

早期不要让每个 agent 都完全依赖 LLM。更现实的做法是：大部分时间使用规则、状态机或 utility AI；只有关键决策、复杂对话、知识总结和计划生成才调用 LLM。

### 2.3 知识自进化系统

可以借鉴 llm-wiki 的思想，但不要把知识保存成散乱聊天记录。知识应结构化。

示例数据结构：

```text
KnowledgeClaim
- id
- subject: "森林北边的井"
- claim: "夜晚会发光"
- source: agent / player / observation / rumor
- confidence: 0.2 ~ 1.0
- scope: private / group / public
- createdAt
- contradictedBy[]
```

Agent 应该能围绕知识做这些操作：

- 观察：从环境事件中得到新 claim。
- 总结：把多条事件压缩成稳定知识。
- 传播：通过对话、公告、书写等方式扩散。
- 质疑：发现冲突信息后降低置信度或创建反证。
- 修正：用新证据更新旧知识。
- 固化：公共知识进入“小镇百科”或档案馆。

关键点是：小镇的知识不是开发者一次写死，而是在 agent 和玩家行动中持续变化。

### 2.4 创造系统

Agent 不只是消费已有规则，还可以组合知识产生新物品、制度、传闻或组织。

示例：

- 木头 + 铁片 + 工匠知识 -> 简易水车。
- 多人相信“井有问题” -> 形成调查小组。
- 某 agent 写下观察 -> 变成公共档案。
- 玩家发布规则 -> 被 agent 理解、误解或反抗。

第一版创造系统不需要开放到任意生成。可以先做“模板化创造”：

- 物品创造：基于资源和技能解锁。
- 组织创造：基于共同目标和关系网络形成。
- 知识创造：基于观察、推理和总结生成。
- 制度创造：基于公共冲突和投票/镇长命令生成。

### 2.5 开发者与小镇双向迭代

这个项目最有价值的方向是“开发者创建环境 <-> agent 自我意识”的闭环。

开发者不是写死剧情，而是通过世界补丁影响小镇：

- 添加新地点。
- 修改资源规则。
- 投放事件。
- 调整 agent 行为模型。
- 审阅 agent 产生的新知识，选择是否固化为世界规则。

Agent 和玩家则反过来通过行动、日志、知识和社会结构告诉开发者：当前世界哪些规则有效，哪些规则产生了有趣结果，哪些规则需要补充。

## 3. 初步选题：主题与世界观

第一版不建议做宏大开放世界，而应做封闭小镇实验场。

推荐主题：

> 边境小镇 / 新移民小镇

理由：

- 每个 agent 都有明确动机：生存、工作、社交、探索、建设。
- 世界规则容易解释：资源有限、岗位有限、天气变化、公共事务。
- 知识进化自然成立：地图未知、传闻传播、制度形成、技术改良。
- 真人玩家加入也合理：可以是新居民、镇长、记者、商人或观察员。

第一版世界观可以这样描述：

> K-town 是一座刚建立的小镇。镇民来自不同地方，他们不知道这个地方的全部规则。森林、矿洞、旧遗迹、河流和市场会不断产生事件。镇民需要通过观察、交流、试错和记录来理解世界，并逐渐建立自己的生活秩序。

风格建议：

- 机制上半写实：体力、资源、时间、地点、关系、记忆都要稳定存在。
- 表达上轻人文：不要一开始追求严肃文学，但要保留人物动机、误解、冲突和情感。
- 美术上 2D 抽象优先：先保证信息表达和系统可调试，再追求复杂视觉。

## 4. 技术栈与系统架构

当前设想的 Godot + C# 客户端、Go 后端是合理的。但 1000+ 智能体必须分层处理，不能每个 tick 都调用 LLM。

建议架构：

```text
Godot 2D Client
  - 渲染地图、角色、UI、玩家操作
  - WebSocket 接收世界状态
  - HTTP/WS 发送玩家动作

Go Game Server
  - 世界 tick
  - 地图/位置/物理简化
  - agent 状态机
  - 事件总线
  - 实时同步
  - 权限和玩家会话

Agent Runtime
  - 快速规则决策：Go 内部
  - 重要决策：LLM 调用
  - 批量总结：异步 worker
  - 记忆压缩：异步 worker

Knowledge / Memory Store
  - PostgreSQL：结构化状态
  - pgvector 或 Qdrant：语义记忆
  - Redis：短期状态、队列、缓存
  - ClickHouse 或 Loki：高吞吐日志

Observability
  - 事件日志
  - agent 决策日志
  - LLM prompt/response 摘要
  - 世界快照
  - replay/debug 工具
```

### 4.1 Agent 执行策略

建议把 agent 分为三层：

1. 冷 agent  
   不在玩家附近，也没有关键事件。低频更新，只做日程推进和摘要状态变化。

2. 温 agent  
   在小镇活跃区域，有社交、工作或探索行为。使用规则和 utility AI 高频决策，偶尔调用 LLM。

3. 热 agent  
   正在和玩家交互，或处于关键剧情/冲突/创造事件中。允许更高频率的 LLM 对话和规划。

这样才能支撑 1000+ agent。

### 4.2 日志系统

日志系统应从第一天设计，因为它会同时承担 debug、replay、知识生成、自动总结和 AI 开发上下文的作用。

建议至少有三类日志。

世界事件日志：

```text
WorldEventLog
- tick
- actorId
- eventType
- locationId
- payload
- causedBy
- visibleTo
- createdAt
```

Agent 决策日志：

```text
AgentDecisionLog
- agentId
- inputSummary
- selectedGoal
- selectedAction
- reason
- modelUsed
- tokenCost
- createdAt
```

知识变化日志：

```text
KnowledgeChangeLog
- claimId
- operation: create/update/dispute/promote/archive
- source
- confidenceBefore
- confidenceAfter
- createdAt
```

后续可以基于这些日志生成：

- 小镇日报。
- Agent 个人日记。
- 开发者调试报告。
- 世界状态 replay。
- AI agent 的上下文摘要。

## 5. 借鉴 comfyui-remote 的开发流程

comfyui-remote 最关键的不是文档多，而是它把 AI 开发变成了可执行计划系统。

可以抽象为六条流程思想。

### 5.1 大功能先写 PRD

先定义目标、非目标、核心体验、风险和验收标准，再让 AI 写代码。

对于 K-town，每个核心系统都应先有 PRD：

- Agent System PRD
- Knowledge Evolution PRD
- World Event Log PRD
- Godot Client PRD
- Go Backend PRD
- Replay and Debug Tool PRD

### 5.2 PRD 后写 Implementation Plan

每份 plan 应包含：

- Goal
- Architecture
- File Structure
- Task 拆分
- 每个 Task 的修改文件
- 数据模型和 API
- 测试方式
- 验收标准
- 建议 commit message

模板：

```md
# 功能名 Implementation Plan

Goal:
一句话说明最终目标。

Architecture:
说明新增状态、数据流、核心模块关系。

File Structure:
| Action | Path | Responsibility |
| --- | --- | --- |

Task 1: 数据模型/类型
- [ ] Step 1...
- [ ] Step 2...
- [ ] Run: ...
- [ ] Commit: feat(scope): ...

Task 2: 后端服务
...

Task 3: UI
...

Acceptance:
- [ ] 构建通过
- [ ] 关键 API 返回正确
- [ ] 数据可恢复/可审计
- [ ] 指定边界条件通过
```

### 5.3 每个 Task 都可独立 commit

不要写“实现整个 agent 系统”这种任务。应拆成：

- 添加 Agent schema。
- 添加 world event log。
- 实现 tick loop。
- 实现 agent memory repository。
- 实现第一个 NPC 日程。
- 添加 replay viewer。

这样才能形成高频稳定 push。

### 5.4 文档是 AI 的上下文缓存

每完成一个阶段，都应更新：

- `docs/development-progress.md`
- `docs/architecture/overview.md`
- `docs/plans/YYYY-MM-DD-feature.md`
- `docs/handoff.md`

目标是让任何新的 Claude Code、HermesAgent 或 Codex session 都能从文档恢复上下文，而不是重新扫描全仓库。

### 5.5 大改用子代理

可以按边界分工：

- 一个 agent 写 Go server。
- 一个 agent 写 Godot client。
- 一个 agent 写 schema + migrations。
- 一个 agent 写文档和测试计划。
- 主 agent 只做集成、review 和返工。

当改动超过 3 个文件或 100 行时，建议强制先写 plan，再分派子任务。

### 5.6 每次结束都留下可恢复状态

每轮开发结束必须留下：

- 当前完成了什么。
- 哪些测试通过。
- 哪些风险还在。
- 下一步从哪里开始。

这可以写入 `docs/handoff.md`。

## 7. 第一阶段建议目标

不要先做 1000 agent。第一阶段建议目标：

> 一个 2D 小镇地图，10 个 agent，3 个地点，5 种事件，agent 能移动、观察、记录知识、简单对话、传播传闻，玩家能进入小镇并影响其中一个事件。

v0.1 验收标准：

- Godot 能显示地图和 agent 移动。
- Go server 有 tick loop。
- agent 有日程和简单目标选择。
- 所有行为写入事件日志。
- agent 能从观察生成 `KnowledgeClaim`。
- 两个 agent 交流后，知识能传播或变形。
- 玩家能制造一个事件，并被 agent 观察到。
- 有一个后台页面或日志工具能查看当天小镇历史。

这个目标足够小，但能验证 K-town 最关键的闭环：环境产生事件，agent 感知事件，知识发生变化，社交传播知识，玩家和开发者可以观察并继续调整世界。

## 8. 下一步建议

建议下一步先写三份文档：

1. `docs/product/vision.md`  
   固化 K-town 的长期目标、非目标、核心体验。

2. `docs/product/world-v0.1.md`  
   定义第一版小镇、地点、资源、事件类型和世界观边界。

3. `docs/plans/2026-05-28-v0.1-prototype.md`  
   把 v0.1 原型拆成可由 AI agent 执行的任务，包括 Godot client、Go backend、日志系统和知识系统的最小实现。

在这三份文档完成前，不建议直接开始写大量代码。当前项目最大的风险不是技术选型，而是目标过大、系统边界不清、LLM 调用策略不可控。先把 v0.1 的可验证闭环做小，后续再扩展到更多 agent 和更复杂社会系统。
