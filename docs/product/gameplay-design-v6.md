# K-town 玩法设计 v6：四周小镇生活 Demo

> **状态**：当前四周 Demo 的交付基线；继承 v5 的“玩家是普通居民、小镇会自己生活并回应选择”原则。
> **日期**：2026-08-25
> **关联文档**：`gameplay-design-v5.md`、`world-view-v3.md`、`art-direction-v2.md`、`docs/plans/2026-08-25-multiweek-demo-plan.md`

## 0. 结论

K-town 的玩法已经形成一个可扩展的多周 Demo，而不是一组互相独立的系统：

```text
看见今天的压力
  → 选择一个居民请求或公共问题
  → 在不同地点付出时间 / AP / 关系机会
  → 立即留下场景、知识、关系或资源变化
  → 居民继续自主行动
  → 次日看到“因为 X，所以 Y”
  → 每周结算一次取舍，并把标记带入下一周
```

玩家不需要完成所有内容才能继续。未处理的请求会被居民自行解决、留下遗憾或过期；玩家改变的是速度、代价、信任和谁承担后果。

## 1. Demo 范围

### 1.1 四周节奏

| 周次 | 解锁日 | 篇章 | 核心压力 | 玩家要作出的判断 |
|---|---:|---|---|---|
| 第 1 周 | 第 1 天 | 雨前的七天 | 暴雨、工坊屋顶、干木料、旧矿道传闻 | 先救眼前的人，还是先确认更大的风险 |
| 第 2 周 | 第 8 天 | 河水改道 | 学校蓄水槽、旧矿道安全路线 | 先做可靠的安全方案，还是接受更快但不完整的办法 |
| 第 3 周 | 第 15 天 | 灯火与账本 | 商路公开、学校借灯、矿石灯火 | 外来机会、镇内照顾与安全之间如何分配 |
| 第 4 周 | 第 22 天 | 归灯集 | 商队到来、居民同桌、公开商议 | 让谁被看见、谁先被照顾、谁来共同决定 |

第 29 天进入最终篇章结算。四周不是四条平行任务列表：前一周的选择通过 `campaign_markers`、关系、知识和准备度影响后续人物语气、可见场景与最终评价。

### 1.2 保留与非目标

保留：

- 12 个 Agent 的身份、人格、记忆、目标、关系与情绪；
- 5 个地点、天气、知识传播、危机、日志、存档和确定性回放；
- 玩家与 NPC 共用 `ActionResolver`，一次动作只校验、扣 AP、推进时间、写日志一次；
- HTML/CSS/vanilla JS 的轻量前端，不引入构建链作为 Demo 前置条件。

当前不作为 Demo 完成门槛：

- 多玩家、1000 Agent、日常 LLM 驱动行为；
- 复杂生产链、技能树、排行榜和全地点升级；
- 把失忆、玉佩、十三时或大缓变设为首周必做主线；
- 让每个居民都拥有独立长篇请求；
- 为每个新章节复制一套 API、前端状态或时间扣费逻辑。

## 2. 每日可玩循环

每天由底层 20 tick 世界时钟驱动，产品界面仍以“清晨、上午、午后、傍晚、入夜、深夜”理解行动。玩家通常有 2–3 次有意义的行动，然后休息进入下一天。

1. 首屏读“小镇脉搏”和“今日三条线”。
2. 从居民请求、公共压力、可验证线索中选择一个方向。
3. 移动到相关地点，执行观察、工作、调查、对话或请求回应。
4. 立刻看到成本、行动结果、变化记录和 `next_observation`。
5. 居民在同一世界里继续自主决定；玩家离开面板不会暂停模拟。
6. 傍晚/次日由事件流、居民档案、地点视觉和日报展示后果。

每个面向玩家的选择至少要提供：对象、成本、即时结果、可能风险、下一次观察点。纯“工作一次 +1”只允许作为底层原语，不能作为章节目标文案。

## 3. 请求与章节内容模型

请求是玩法内容的基本单位，包含：

```text
id / chapter_id / requester / location / situation / deadline
options[]: requires / cost_ap / cost_hours / effect / result_desc
         next_day_observation / visible_risk / closes_request
status: active | completed | expired
```

新增请求的流程：

1. 在 `requests.py` 中写数据定义和至少两种有方向差异的选项。
2. 在 `campaign.py` 中注册所属章节和结构化 `effect`。
3. 由 `ActionResolver` 负责地点、前置、截止日、AP、时间和日志。
4. 由 `CampaignDirector` 解释章节效果，写入分数、旗标、场景标记、关系和知识。
5. API 只暴露稳定请求/行动结果契约，前端不认识 effect 字符串。
6. 用跨天测试确认即时结果和次日后果都可观察。

### 3.1 四周内容接入边界

| 内容 | 入口 | 结果落点 |
|---|---|---|
| 首周居民请求 | `seed_initial_requests()` | 请求状态、关系、屋顶/传闻等世界状态 |
| 第 2–4 周请求 | `seed_chapter_requests(chapter_id)` | `CampaignDirector` 的 flag、score、marker、knowledge |
| 周章解锁 | `CampaignDirector.sync_for_day()` | 章节事件、请求注册、章节历史 |
| 终局结算 | 第 29 天导演结算 | `final_outcome`、结局标题、总结与指标 |

章节内容不直接修改 tick 主循环，不在前端写分支，不绕开 ActionResolver。

## 4. 选择与结局

章节效果使用四个可解释指标：

- `care`：镇内照顾、弱势居民和公共生活被优先考虑的程度；
- `safety`：路线、设施、风险判断和实际准备度；
- `trust`：居民是否愿意坦诚、共同承担和公开商议；
- `welcome`：小镇是否愿意接纳外来商队与新的交换关系。

指标不是单一分数游戏，而是把玩家跨周取舍留在世界里的摘要。最终结局根据最高倾向与关键旗标组合生成，例如：

| 组合倾向 | 结局方向 |
|---|---|
| care + trust | 居民共同守住归灯集，关系最稳 |
| safety + care | 镇子更安全，但对外来机会更谨慎 |
| welcome + trust | 商队留下，小镇开始与外部建立新约定 |
| welcome 高但 safety 低 | 机会到来，同时留下路线与风险隐患 |
| 多条请求未完成 | 归灯集仍会举行，但由居民补救，玩家看到真实遗憾而不是 Game Over |

具体阈值和文案由 `CampaignDirector` 管理；前端只渲染 `campaign` 载荷，不复制结局判断。

## 5. 前端体验基线

主屏信息层级固定为：

1. 小镇脉搏：地点活动、心情、流传中的知识、玩家位置；
2. 当前篇章卡：本周压力、目标、评分、章节进度和下周预告；
3. 今日三条线：居民请求、镇上压力、可跟进线索；
4. 当前地点上下文行动：按钮必须显示对象与成本；
5. 居民档案、请求详情、动态、知识流作为展开层。

移动端保留篇章卡、今日三条线和行动入口；侧栏变为可滚动区域/底部 sheet，不通过隐藏核心玩法来解决空间问题。`prefers-reduced-motion` 必须降低粒子、过渡和地图动画。

## 6. 完成定义

四周 Demo 视为完成，需要同时满足：

- 第 1–4 周按日解锁，章节请求能从 API/state/前端看见；
- 每周至少两条请求或分支可通过统一 resolver 完成，成本和结果不同；
- 周章选择写入可恢复的 campaign state，并影响 marker、知识、关系、评分或结局；
- 第 29 天能得到稳定、可解释的最终篇章结局；
- 保存/恢复后章节、请求、旗标、分数、世界标记和结局一致；
- 前端状态由稳定契约驱动，新增章节不要求复制主应用事件处理；
- 完整测试、API 健康检查、桌面/390px/reduced-motion 验收通过；
- 文档、交接记录、测试数据库和临时产物保持清洁。
