# K-town 玩法设计 v5.0：住进一座会回应你的镇子

> **状态**：当前体验基线，取代 v4 作为新功能评审依据
> **日期**：2026-08-23
> **读者**：策划、程序、美术、后续 AI coding session
> **关联文档**：`world-view-v3.md`、`art-direction-v2.md`、`docs/plans/2026-08-23-rebuild-plan.md`

## 0. 先说结论

K-town 现在不是缺系统，而是系统没有被组织成一个玩家能理解的选择循环。v0.5 已经有情绪、危机、知识、重建、任务和身世线，但玩家首屏看到的是地图、统计和一排抽象按钮，做完动作后也很难回答：

> 我刚才帮了谁？我放弃了什么？小镇明天会有什么不同？

v5 只围绕一个答案展开：

> **K-town 是一座会自己生活的小镇。玩家以普通新居民身份暂住七天，在有限时间里决定帮助谁、相信什么、把时间留给哪里；第二天，小镇会用居民行为、关系和场景变化回应这个选择。**

这不是“建设模拟器”、不是“收集谜题的英雄 RPG”，也不是“看数字跳动的监控台”。小镇是主角，玩家是会被小镇记住的一位住民。

## 1. 设计诊断

### 1.1 当前体验断点

| 现象 | 玩家感受 | v5 的处理 |
|---|---|---|
| 底栏同时摆出移动、工作、调查、休息、知识、重置 | 行动没有对象，也没有取舍 | 改为当前地点的 2-4 个具体回应 |
| 任务按工作/移动次数计数 | 像待办清单，不像生活 | 改为有请求人、期限、风险、后果的请求 |
| 情绪有规则但只显示旧 mood | 看不到“因为所以” | 档案显示“感受 → 原因 → 倾向 → 你能回应什么” |
| 危机与进度已有后端接口但前端不可见 | 系统等于不存在 | 先接入一条可操作的天气压力线 |
| 20 小时、十三时、失忆、末世谜团同时出现 | 新手不知道应该关心谁 | 日常小镇先讲清，谜团降为后期支线 |
| 地图每次只聚焦一个地点 | 看不见小镇同时生活 | 默认展示全镇活动，点击地点打开上下文 |

### 1.2 评审规则

以后任何新系统必须回答四个问题，否则不进入当前版本：

1. 玩家在什么场景中看见它？
2. 玩家做什么具体选择？
3. 选择的即时反馈是什么？
4. 玩家在下一时段或第二天在哪里看到后果？

## 2. 产品边界

### 2.1 当前版本目标：七天纵切片

第一目标不是“模拟更多天”，而是让玩家在 5 分钟内经历一次完整的小镇选择：

```text
看见居民处境 → 选择一条回应 → 付出时间/资源 → 立即改变一个人或一个场景
→ 傍晚看到因果记录 → 次日看到后果
```

首个可玩纵切片固定为：

- 7 个游戏日；
- 12 位居民的数据仍保留，但首周只有 6 位是高频活动者；
- 3 位有手写请求的核心居民：托林、莉娜、梅奶奶；
- 3 个地点承担主要玩法：广场、工坊、河谷野径（代码 ID 可暂时沿用 `square/workshop/wilderness`）；
- 1 个持续压力：预告中的暴雨会威胁工坊屋顶和干木料；
- 1 条可传播的传闻：旧矿道是否安全；
- 1 个可见重建项目：工坊屋顶从漏雨到修好；
- 1 次明确的情绪 → 行为 → 习惯改变；
- 1 个傍晚因果总结和 1 个次日场景变化。

完成纵切片后，玩家应该能够复述：

> “我帮了谁，放弃了什么；因此谁和谁的关系变了；第二天哪个地方不一样。”

### 2.2 暂时不追求

- 不追求 1000 个 Agent、真强化学习或日常 LLM 决策；
- 不追求复杂生产链、技能树、成就、声望和排行榜；
- 不追求每一种危机都可玩；
- 不追求第一周解释大缓变、失忆和十三时；
- 不追求同时支持多玩家；
- 不追求地图上的每个建筑都能升级。

## 3. 新世界观与玩家位置

详细设定见 `world-view-v3.md`。玩法层只依赖以下事实：

- K-town 是河谷尽头的普通边境小镇，居民没有镇长，遇到大事在广场商量；
- 七天后小镇要举办“归灯集”，外来商队是否停留取决于小镇是否维持住互助、信任和基本修缮；
- 玩家是决定暂住一周的新居民，不是救世主、镇长或被选中的人；
- 居民有自己的目标和关系，即使玩家不帮忙也会自行行动；
- 旧世界遗迹、大缓变、玉佩和十三时仍可保留为后期可选发现，但不能成为首日教学或主循环门槛。

## 4. 核心循环

### 4.1 一日循环

```text
晨间脉搏
  ↓ 天气、居民请求、镇上压力、可跟进的线索
选择一条线
  ↓ 具体对象 + 明确代价 + 至少两种做法
执行 2-3 个时段行动
  ↓ 居民自主反应，关系/情绪/资源/场景发生变化
傍晚广场
  ↓ 看见谁互相帮助、谁改变了想法、哪条传闻在传播
休息
  ↓ 生成“因为 X，所以 Y”的次日简报
次日观察后果
```

### 4.2 玩家时间

引擎可以暂时保留 20 tick 的世界时钟，但产品界面不再让玩家数 12 个抽象 AP。纵切片采用 6 个玩家时段：清晨、上午、午后、傍晚、入夜、深夜。一个行动消耗 1-2 个时段，睡觉结束当天。

迁移期间通过适配层映射到现有 AP；在 `ActionResolver` 接入前，不允许 API 和 `_handle_action` 各自扣一次时间。

### 4.3 请求（Request）而非任务（Quest）

请求是玩家真正要处理的内容。每个请求必须包含：

```text
请求人 / 地点 / 当前处境 / 截止时间
至少两种回应 / 时间或资源成本 / 可预见风险
即时反馈 / 可能影响的居民和关系 / 次日可观察后果
```

示例：托林的工坊屋顶漏雨。

| 回应 | 成本 | 风险与方向性后果 |
|---|---:|---|
| 独自去河谷找干木料 | 2 时段 | 稳定拿到材料，但错过和莉娜交流的机会 |
| 先请莉娜一起规划 | 1 时段 | 关系改善，后续修缮更快，但当天材料不足的风险上升 |
| 留在工坊先补临时遮雨层 | 2 时段 | 屋顶暂时安全，消耗旧布料，托林立即信任你 |

“工作一次”“移动一次”“调查一次”只能作为底层动作类型，不能直接作为玩家目标文案。

## 5. 保留、重做与冻结

### 5.1 保留为底层能力

- Agent 身份、人格、记忆、目标、关系；
- 四维情绪和情绪传染；
- 结构化知识：传闻、证据、相信者、置信度、冲突；
- 天气、食物、基础材料和一个可见修缮项目；
- NPC 自主行动和不依赖玩家的自救；
- SQLite 日志、回放和确定性测试能力。

### 5.2 重新接线

- `tick.py`：所有玩家、NPC、对话、危机行动走同一个 `ActionResolver`；
- `agent.py`：把“观察到什么 → 为什么这样选”写入短期记忆和行动结果；
- `api.py`：只接受合法的玩家身份、目标地点和同地点交互；
- `quests.py`：改名为请求/压力内容层，删除纯计数目标；
- 前端：以请求、因果和场景反馈为主，不直接暴露内部系统数量。

### 5.3 冻结到纵切片之后

- 20 小时设定作为 UI 主概念；
- 失忆旅行者、玉佩、十三时和大缓变主线；
- 随机危机池、复杂交易生产链、派系；
- 技能树、成就、声望、排行榜；
- 世界自生成、LLM 驱动日常行为；
- 12 位居民全部同时拥有独立剧情请求。

冻结不是删除。代码和文档保留，但任何新工作不得依赖这些系统才能完成首周循环。

## 6. 情绪与知识如何服务玩法

### 6.1 情绪不做 HUD 数值墙

后台仍保留 `joy/anxiety/anger/sadness`，前端优先显示：

```text
此刻感受：焦虑
原因：连续两天没有干木料，明天又要下雨
行为倾向：更愿意独自做事，不想承诺帮忙
玩家可回应：先陪她去找材料 / 给她带来传闻 / 暂时不打扰
```

四维条形只在档案详情中作为可展开的解释，不作为首屏主要目标。

### 6.2 知识做成社会流动

玩家看到的不是知识数据库，而是：

```text
谁发现 → 谁相信 → 谁转述 → 谁质疑 → 哪个行动受影响
```

“旧矿道有塌方”必须能在事件流、居民档案或请求中至少出现一次可见后果，否则它只是无用文本。

### 6.3 因果记录

每次重要行动写一条结构化记录：

```json
{
  "actor": "agent_player",
  "action": "bring_dry_wood",
  "reason": "lina_requested_material",
  "changes": ["workshop_roof_progress+1", "lina_trust+2"],
  "next_observation": "day_2_workshop_open"
}
```

日报只挑最重要的 3 条，句式统一为“因为……所以……”。

## 7. 首次体验与引导

### 7.1 前五分钟脚本

1. 晨雨中的广场，梅奶奶递来一张“今日小镇脉搏”，只显示天气和三条线索；
2. 高亮托林，档案显示“担心什么、正在做什么、希望谁帮忙”；
3. 玩家打开工坊或河谷野径，看到两到三个具体回应；
4. 选择一个回应后，舞台立即显示人物移动、材料减少、屋顶状态或关系变化；
5. 傍晚出现一张因果回信，告诉玩家明天会观察到什么；
6. 引导在玩家完成第一步后逐渐消失，不能用一张长说明书替代游戏。

### 7.2 引导验收

- 首屏不超过 3 个高亮入口；
- 第一个动作必须有明确对象；
- 任何按钮面上显示时间成本和作用方向；
- 不把“重置”放在日常行动栏；
- 新玩家 5 分钟内完成一次选择并看到即时反馈；
- 重新打开引导只能通过帮助入口，不能重复遮挡首屏。

## 8. UI 信息架构

### 8.1 主屏：生活舞台

- 中央：全镇/当前地点的居民活动、天气、修缮状态；
- 右侧：今日三条线（居民请求、镇上压力、值得跟进的线索）；
- 底部：当前地点的上下文行动卡；
- 点击居民：感受 → 原因 → 正在做什么 → 请求/可回应；
- 傍晚：事件册/因果回信；
- 移动端：右侧内容变为底部抽屉，不得直接隐藏。

### 8.2 绝不把内部状态直接堆给玩家

金币、体力、AP、置信度和情绪四维仍可在详情查看，但首屏只呈现与当前选择有关的成本和方向。调试信息放入单独的开发抽屉。

## 9. 验收标准

### P0：可玩闭环

- 玩家可在 7 天内完成至少 3 个请求；
- 每个请求有两个以上有效回应，且回应有不同代价或后果；
- 玩家动作只扣一次时间，世界只推进一次；
- NPC 会接收到事件并在决策中留下可追溯原因；
- 日报能生成至少 3 条真实“因为 X，所以 Y”；
- 保存/读取后时钟、地点、关系、情绪、库存、知识和请求状态一致；
- 冒烟测试使用独立数据库，不改写默认存档。

### P1：可读的居民

- 同一事件对两种人格产生不同情绪和行动；
- 档案能显示当前处境和行为原因；
- 知识传播至少改变一个居民的选择；
- 玩家能在次日看到一次场景或关系后果。

### P2：生活感与美术

- 中央舞台默认能看到多个地点或多个居民活动；
- 天气、修缮、傍晚和事件有稳定的视觉反馈；
- 移动端仍能看到今日三条线和行动入口；
- 视觉资产统一为绘本水彩舞台，不再混用无规则的像素和仪表盘卡片。
